## 2. Identita, souběh a zachování polí

- `cloudUrl` sestavuje URL z aktuálního globálního tokenu. Starší `secure*Request` čekají na ensureCloudToken bez zachyceného operačního ticketu. To není stejná záruka jako v9b2/9c. Profilová práva, canManageTournament/Series, vlastnictví rozehraného zápasu a system-admin nejsou totéž co platný token; skutečné serverové omezení jsou Rules, jejichž aktuální kopie v repozitáři chybí.
- Bezpečnější nasazené vzory: PlayersReader má UID+profile/role/ověření scope, epoch/revision a beginWrite bariéru; MatchChallengeActions vlastní UID/profil/generaci a whitelisted deltu; CloudRefresh, hlášení, FC/Livescore a OnlinePresence mají vlastní generační platnost. Zachovat také kontrolu **po JSON decode**, při A→B→A a při změně role stejného UID.
- Všechny obecné celopoložkové PUT mohou přepsat novější souběžné serverové změny. `saveSecurePlayer` negarantuje čerstvou serverovou obálku; `serializeProfile` výzev zachová neznámá pole **aktuálně známé obálky**, není to CAS proti dalšímu zařízení. BeginWrite brání jen starému sdílenému GET, nikoli všem obecným writerům či ostatním zařízením.
- FC save zachová ostatní root/data pole a mění jen federalCup2026 přes If-Match. Generic appData upload vytváří `{updatedAt,data}` a používá merge s pevnou sadou domén; ETag chrání souběh snapshotu, **negarantuje zachování libovolných neznámých polí schématu**. Historical persist má expected fingerprint, revision, ETag, creationKey a následný GET; to není univerzální důkaz dokončení libovolné ztracené operace. PATCH turnajového skóre má užší rozsah; potvrzení zápasu zapisuje jen podvětev UID.
- Mazání: fyzické DELETE hráče/zápasu/turnaje, vedlejší `/users/{uid}/playerId` unlink a lokální tombstones nejsou jedna transakce. Explicitní push deletedMatchIds je v delete flow15434; deletedTournamentIds se v tomto core normalizují a slučují, není to obecná automatická součást každého secure DELETE. Match tombstones se z globálního appData payloadu záměrně vyjímají. Reconcile/import/normalizace nesmí při přesunu znovu oživit smazaný záznam. Zachovat neznámá serverová pole při stávajícím PUT; nové vlastní snapshoty/delty sestavovat whitelisty, nikoli potichu sanitizovat celou existující obálku.

## 5. Přesná první implementace10a — zatím jen doporučení

- Jeden produkční `assets/js/players-read-repository.js` s `create(...)`; přesunout **celé** dnešní `MatchChallenges.createPlayersReader` a odpovídající jediný GET players adapter z index8472+. MatchChallenges pak vlastní pouze challenge cache/merge/globální obnovy a používá stejný aplikační `loadSecurePlayers`; nevytváří další reader.
- Návrhové rozhraní: `read()`, `syncIdentity()`, `beginWrite()`→idempotentní release, `dispose()`, `snapshot()` pro testy. `beginWrite` je **bariéra čtení**, ne serverový zápis. Zachovat všechny známé chybové výsledky a rejection semantics, rezervovat Promise před authorize, kontrolovat platnost po JSON a při release staré relace. Žádný GETbyId/save/delete v10a.
- Explicitní závislosti: identity UID+profile/role/ověření scope, authorize(request.current/signal), fetch, playersUrl/clock a publishSnapshot callback. URL/credential se sestaví pouze pro platný ticket těsně před GET, tokeny se neukládají do snapshotů/logů. Repository nemá DOM, časovače/polling, localStorage, herní pravidla, claim repair ani cloudový PUT/PATCH/DELETE; vrací nezkrácenou mapu včetně neznámých serverových polí. Callback v aplikaci při platné relaci aplikuje data a stávající render.
- **Vlastníci se nemění:** existuje jedna app-owned instance securePlayersReader; současné sync místo9045, write barrier9b2 a pagehide/disposal přes `MatchChallenges.onDispose`29159 zůstanou propojené. ChallengeReader stále vlastní své timery, cloud/report/Livescore/presence vlastní své. První PR neprovádí plošný přesun bootstrapu nebo přihlášení.
- Zachovat login/profile repair/dashboard/challenge volající a payloady; obecné securePlayerRequest/saveSecurePlayer a data formáty se zatím nemění. Auth refresh může mít svůj POST, ale read repository nezahajuje RTDB data zápis. Neprohlašovat celý login či navigaci za bez zápisů jen proto, že je jeho players read čistý.
- Hotovo jen při jediné produkčně načítané implementaci bez exportu starého factory/fallbacku, přepojených testech na nový skutečný modul, shodě dat/pohledů a prokazatelně zachované bariéře9b2. Verzi určit **až při implementaci** z tehdejšího main; nynější dokumentační návrh112 nezvyšuje. První návrat je revert celého10a bez dat; staré aktuální behavior se tím obnoví.

## 6. Ověření a potřebné Auth/Rules prostředí

1. **Baseline na přesném aktuálním main:** skutečný nezměněný export jen v izolovanéRAM, struktura+hash dat před/po, počty GET/PUT a prostředků. Stejné vstupy pro obě varianty, nerozdílné sportovní výpočty. Doložené opravy112 se nesmějí vrátit na111, preserve openingBreakAvailable14/UNDO i mobilníCI.
2. **10a unit nad produkčním modulem:** současné read/barrier testy9b přepojit, zachovat nezávislé očekávání; null/empty/malformedJSON,401/403/offline, expirace tokenu, A-B-A/stejnéUID-jinárole, logout během authorize/decode, backend ignorujícíAbort, nestedbarrier a starý release po přepnutí účtu.0RTDBmutací,1GET pro souběh, žádný růst prostředků, žádná tokenová data v metadatech; porovnat nezkrácená serverová pole a nevyrábět nuly.
